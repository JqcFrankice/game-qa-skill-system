# XMind 测试点书写规范

> 所属板块: 流程与工具能力 | 编号: T10 | 最后更新: 2026-07-10

## 1. 适用范围

本规范适用于“测试点脑图”类 XMind，主要用于冒烟测试、功能点梳理、评审沟通和回归范围确认。

它不等同于详细测试用例。详细用例需要包含步骤、预期、优先级等字段；测试点脑图强调模块结构清晰、覆盖范围完整、节点颗粒度适合快速执行。

### 1.1 与详细测试用例的路由边界

| 用户目标 | 使用规范 | 输出叶子结构 |
| --- | --- | --- |
| 冒烟测试点、评审脑图、回归范围 | T10（本规范） | `测试点 -> S/A/B` |
| 详细测试用例、可执行步骤、明确预期 | T08 + `testcase-xmind-format` | `TC -> 步骤 -> 预期 -> P0/P1/P2` |

- 用户明确要求“测试点脑图”“冒烟 XMind”或 `S/A/B` 时，使用 T10。
- 用户要求详细用例、步骤和预期时，使用 T08；不得把两种叶子结构混在同一产物中。
- 需要从测试点升级为详细用例时，保留模块结构，并为每个测试点补充独立 TC、步骤、预期和 P0/P1/P2。

## 2. 基础结构

推荐结构：

```text
中心主题：功能名称
├── 一级分支：功能域/业务模块
│   ├── 二级分支：测试分类/能力点
│   │   ├── 三级分支：具体测试点
│   │   │   └── 等级节点：S / A / B
```

示例：

```text
功能名称
├── 功能入口
│   └── 解锁条件
│       ├── 满足配置条件后入口可见并可进入
│       │   └── S
│       └── 未满足配置条件时入口隐藏或不可进入
│           └── S
```

## 3. 层级定义

| 层级 | 含义 | 写法要求 |
| --- | --- | --- |
| 中心主题 | 被测功能名称 | 使用功能名，不写版本号、需求背景或长句 |
| 一级分支 | 功能域/主模块 | 按玩家使用路径或系统能力拆分，如入口、核心操作、规则、设置、奖励 |
| 二级分支 | 测试分类 | 描述同一能力下的测试方向，如准入校验、提交操作、状态同步、异常限制 |
| 三级及以下分支 | 具体测试点 | 用一句话表达条件、操作和验证目标 |
| 叶子节点 | 测试等级 | 只写 `S`、`A`、`B`，不混写说明文字 |

## 4. 节点书写规则

### 4.1 功能域要按业务边界拆分

一级分支应是稳定的业务模块，不要按执行人、页面截图或临时备注拆。

推荐：

- 功能入口
- 核心操作
- 规则校验
- 状态展示
- 奖励/消耗
- 设置配置
- 异常恢复
- 外部联动

不推荐：

- 需要测的点
- UI
- 其他
- 问题记录

### 4.2 测试点要表达可验证目标

测试点节点应包含“条件 + 操作/行为 + 预期方向”，让执行人不看需求也能知道要验证什么。

推荐：

- `满足等级和开关配置后，功能入口可见并可进入`
- `未满足准入条件时，入口隐藏或进入请求被拦截`
- `A 执行核心操作后，B 在目标范围内可见，非目标范围不可见`
- `复制或篡改结构化内容后再次提交，按普通文本或非法输入处理`

不推荐：

- `功能测试`
- `看一下`
- `功能正常`
- `UI正确`

### 4.3 同一层级只放同类信息

同一父节点下的子节点应保持同一类型。

例如 `核心操作` 下应放具体操作能力：

- 移动端执行核心操作成功
- PC端执行核心操作成功
- 内容合法性校验
- 复制粘贴或重复提交校验

不要混入“备注”“问题”“策划确认”等非测试点内容。待确认事项应放到单独的“待确认”分支。

### 4.4 等级节点必须挂在测试点下

等级节点是叶子节点，只表示执行优先级：

- `S`：冒烟必测，主流程、核心能力、入口准入、资产/权限/数据安全。
- `A`：重点回归，重要分支、主要状态、常用交互、关键展示。
- `B`：补充覆盖，低频路径、兼容体验、弱边界或非阻断展示。

等级节点不要写成：

- `S级`
- `优先级S`
- `S-必测`
- `P0`

如需和 P0/P1/P2 映射，默认：

| XMind 等级 | 用例优先级 |
| --- | --- |
| S | P0 |
| A | P1 |
| B | P2 |

## 5. 颗粒度规范

### 5.1 冒烟测试点不写完整步骤

冒烟 XMind 只写测试点，不展开详细步骤和预期。

推荐：

```text
操作冷却
├── CD期间不能重复提交，有toast提示
│   └── S
└── CD结束后可再次提交
    └── S
```

不推荐：

```text
CD期间不能重复提交
├── 步骤1：提交一次操作
├── 步骤2：再次提交同一操作
├── 预期：提示冷却中
└── S
```

详细步骤应放在测试用例 Markdown 或测试管理平台中，不放在冒烟测试点脑图中。

### 5.2 一个节点只验证一个核心判断

如果条件、权限、对象、阶段、结果不同，应拆成多个测试点。

推荐：

- `玩家等级达到配置要求，可执行核心操作`
- `玩家等级未达到配置要求，不可执行核心操作`

不推荐：

- `验证等级达到和未达到时功能是否正常`

### 5.3 可复用能力按能力聚合

同一能力在多个模块中复用时，可以按能力聚合，不必为每个页面重复铺开。

例如：

- 内容合法性校验
- 复制粘贴
- CD 限制
- 权限提示
- 他人视角同步

但如果不同业务场景的规则不同，应拆开。

## 6. 冒烟重点覆盖清单

生成或评审 XMind 测试点时，至少检查以下维度：

| 类型 | 必测内容 |
| --- | --- |
| 入口解锁 | 功能是否按等级、任务、配置、FunctionConfig 解锁 |
| 主流程 | 核心操作是否能完成，如进入、选择、提交、领取、结算 |
| 权限边界 | 未达条件、无权限、不同身份是否被正确拦截 |
| 数据可见性 | A 操作后，B 是否按关系、权限、范围正确可见 |
| 状态同步 | 自己视角和他人视角是否一致 |
| 内容安全 | 文本、命名、输入内容、结构化内容是否触发过滤或合法性校验 |
| 消耗/资产 | 道具、货币、次数是否正确扣除或不扣除 |
| 异常限制 | CD、取消、复制篡改、退出、隐藏等是否按规则处理 |
| 设置持久化 | 配置修改后是否立即生效，重登后是否保持 |

## 7. 通用 XMind 推荐结构

常规功能可参考以下模块，并根据业务实际删减：

```text
功能名称
├── 功能入口与解锁
├── 核心操作流程
├── 规则与权限校验
├── 状态展示与反馈
├── 数据变化与资产安全
├── 设置与个性化配置
├── 多端/多视角同步
├── 异常操作与恢复
└── 外部系统联动
```

## 8. 自检清单

提交 XMind 前检查：

- 中心主题是否为明确功能名。
- 一级分支是否覆盖核心业务模块。
- 是否存在“其他”“正常”“检查一下”等模糊节点。
- 叶子节点是否统一为 `S/A/B`。
- 是否有测试点缺少等级节点。
- 是否把详细步骤、预期、备注混入测试点脑图。
- 是否覆盖入口、主流程、权限、可见性、状态同步、异常限制。
- 涉及资产或消耗时，是否有扣除、失败不扣、重复提交防护。
- 涉及多玩家或多端可见性时，是否覆盖自己视角、他人视角、非目标对象不可见。
