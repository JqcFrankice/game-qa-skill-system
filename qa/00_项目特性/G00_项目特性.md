# 项目特性

> 所属板块: 前置基础 | 编号: G00 | 最后更新: 2026-07-10

---

## 1. 概述

项目特性是整个QA技能体系的前置基础，定义了"我们在测什么"。所有后续Skill（F01-F14业务测试、S01-S09专项测试、T01-T10工具流程等）的执行策略、用例设计、自动化方案都应以项目特性为输入。一个清晰的项目特性档案，是测试策略制定、用例生成、自动化脚本编写的起点。

**核心准则：生成用例时优先读取用户显式指定的资料；未指定路径时，再按功能名检索 `openspec/changes/` 和 `examples/requirements/`。不得加载名称不匹配的其他功能文档。**

**核心价值：**
- 为用例生成提供上下文（项目类型决定测试重点）
- 为自动化测试提供基础设施（GM指令是自动化的前置条件）
- 为团队协作提供共识（新人快速理解项目全貌）
- 为AI辅助测试提供Prompt上下文（项目特性 → Gherkin场景生成）

## 5. GM指令集合

### 5.1 概述

GM指令（Game Master Commands）是测试环境中用于快速构造测试条件的命令集合。它是自动化测试的基础设施——没有GM指令，大量测试场景无法高效构造。

**GM指令对自动化的价值：**
- 快速构造前置条件（跳过漫长的手动操作）
- 精确控制游戏状态（设置等级、金币、时间等）
- 可重复的测试环境（每次执行前重置到相同状态）
- 与BDD场景的Given步骤天然对应

### 5.2 GM指令分类标准

| 分类 | 用途 | 示例指令 | 对应Skill |
|------|------|---------|----------|
| 账号类 | 账号状态控制 | `gm set_level 60` / `gm set_vip 10` | F01/F10 |
| 货币类 | 经济数据控制 | `gm add_gold 99999` / `gm add_diamond 1000` | F04/F09 |
| 道具类 | 物品发放/清除 | `gm add_item 10001 99` / `gm clear_bag` | F05 |
| 任务类 | 任务进度控制 | `gm complete_quest 1001` / `gm reset_quest` | F06 |
| 战斗类 | 战斗状态控制 | `gm god_mode on` / `gm set_hp 99999` | F03 |
| 场景类 | 场景跳转 | `gm teleport 100 200` / `gm enter_scene 3001` | E01 |
| 时间类 | 时间控制 | `gm set_time 2026-01-01` / `gm skip_cd` | F11 |
| 系统类 | 系统开关 | `gm open_activity 5001` / `gm set_server_time` | F11/E02 |
| 调试类 | 调试辅助 | `gm show_fps` / `gm show_hitbox` / `gm log_level debug` | S01/T05 |

### 5.3 GM指令登记模板

```yaml
# === GM指令登记 ===
# 每条指令需登记以下信息，用于自动化脚本引用

- command: "gm add_gold {amount}"
  category: "货币类"
  description: "增加金币"
  parameters:
    - name: amount
      type: int
      range: "1-999999999"
  precondition: "角色已创建"
  side_effect: "触发金币变更事件，可能触发成就"
  automation_usage: "Given步骤：构造充足金币的前置条件"
  available_env: ["dev", "qa", "staging"]  # 可用环境
```

### 5.4 GM指令与自动化测试的映射

```gherkin
# GM指令在BDD场景中的典型用法

Feature: 商城购买流程
  Background:
    Given 通过GM指令设置玩家等级为60
    And 通过GM指令添加10000钻石

  Scenario: 购买限购商品
    When 打开商城页面
    And 购买"限定礼包"
    Then 钻石减少对应金额
    And 背包中出现礼包道具
```

对应的自动化步骤定义：
```python
@given('通过GM指令设置玩家等级为{level:d}')
def step_set_level(context, level):
    context.gm.execute(f"gm set_level {level}")
    context.gm.wait_for_effect(timeout=5)

@given('通过GM指令添加{amount:d}钻石')
def step_add_diamond(context, amount):
    context.gm.execute(f"gm add_diamond {amount}")
    context.gm.wait_for_effect(timeout=5)
```

### 5.5 GM指令管理规范

| 规范项 | 要求 | 说明 |
|--------|------|------|
| 命名规范 | `gm {动词}_{名词} {参数}` | 统一格式，便于自动化解析 |
| 权限控制 | 仅限测试环境，生产环境禁用 | 防止线上误操作 |
| 版本同步 | 每次版本更新同步GM指令变更 | 避免自动化脚本因指令变更失败 |
| 文档维护 | 新增/修改/废弃指令必须更新本文档 | 保持指令集合与实际一致 |
| 返回值 | 每条指令返回执行结果（成功/失败/原因） | 自动化脚本需要判断执行结果 |
| 幂等性 | 同一指令重复执行结果一致 | 保证自动化重试的可靠性 |

## 7. 执行流程

### 7.1 项目特性建档（项目启动时）
- 填写项目类型登记模板（2.2节）
- 填写项目基本信息模板（3.1节）
- 填写核心系统清单（3.2节）
- 填写美术与交互风格（4.1节）
- 根据品类映射表确定高优Skill清单

### 7.2 GM指令收集（研发阶段持续）
- 与开发团队对齐GM指令清单
- 按5.3模板逐条登记
- 验证每条指令在测试环境可用
- 建立GM指令与测试场景的映射关系

### 7.3 定期维护（版本迭代时）
- 每个版本检查GM指令变更（新增/修改/废弃）
- 更新项目特性档案（新系统上线、平台扩展等）
- 同步自动化脚本中的GM指令引用

## 8. 踩坑经验库

### 高频踩坑 TOP 5

**坑1：GM指令在不同环境行为不一致**
- 现象：QA环境GM指令正常，Staging环境执行无效
- 原因：Staging环境GM权限被关闭或指令版本不同步
- 解决：建立环境-指令可用性矩阵，自动化脚本执行前先验证GM可用性

**坑2：GM指令有副作用导致测试结果不准**
- 现象：用GM加金币后，触发了成就系统奖励，导致金币数量与预期不符
- 原因：GM指令触发了游戏内事件链
- 解决：登记每条GM指令的副作用（5.3模板中的side_effect字段），测试用例中考虑副作用

**坑3：项目类型判断错误导致测试策略偏差**
- 现象：把"开放世界+MMO"项目按纯MMO策略测试，遗漏了大世界加载相关问题
- 原因：项目品类有交叉，只按主品类制定策略
- 解决：项目类型支持多标签，测试策略取所有相关品类的Skill并集

**坑4：GM指令文档与实际不同步**
- 现象：自动化脚本调用GM指令失败，排查发现指令参数已变更
- 原因：开发修改了GM指令但未通知QA
- 解决：GM指令变更纳入版本发布checklist，CI中增加GM指令可用性检查

**坑5：忽略项目风格对性能测试基线的影响**
- 现象：用通用性能基线评估写实风格游戏，大量误报
- 原因：写实风格GPU/内存消耗天然高于卡通风格
- 解决：性能基线按项目风格分级设定，不使用统一阈值

## 9. 本项目特性档案（从实际测试用例提炼）

> 以下特性从 test_system/ 下 66 个实际测试用例文件中提炼，反映本项目独有的全局规则。所有后续 Skill 的用例设计、自动化脚本需以此为输入上下文。

### P01 游戏日重置：凌晨 4:00

| 维度 | 规则 |
|------|------|
| 日重置时间 | 凌晨 4:00（非自然日 0:00） |
| 周重置时间 | 每周一凌晨 4:00 |
| 必验时间点 | 3:59（不刷新）、4:00（刷新）、12:00（不刷新） |
| 影响范围 | 每日任务、门派捐献次数、门派工资、月卡每日奖励、神武打造次数、活动奖励、活跃度 |
| 在线跨天 | 玩家在线时到达 4:00 → 实时刷新；到达 0:00 → 不刷新 |
| 离线跨天 | 玩家 3:59 离线、4:00 后上线 → 刷新 |

**测试策略**：所有含"每日""每周"字样的功能，均需用 GM 命令 `gm set_server_time` 跳转至 3:59/4:00/12:00 三个时间点验证。

### P02 门派体系

| 维度 | 规则 |
|------|------|
| 初始化 | 服务器初始化创建 4 个门派 |
| 加入机制 | 新玩家按 1→2→3→4→4→3→2→1 循环加入，保持门派人数均衡 |
| 职位层级 | 掌门 > 副掌门 > 长老 > 弟子 |
| 弹劾条件 | 掌门离线时间 ≥ 48 小时，副掌门可发起弹劾；弹劾后 24 小时内掌门未上线 → 弹劾成功 |
| 弹劾继承 | 战力最高的成员获得掌门（战力相同按 UID 排序） |
| 转让冷却 | 转让间隔 ≥ 24 小时；仅可转让给副掌门 |
| 工资公式 | 最终工资 = 基础工资 × 门派等级加成 + 职位加成工资 |
| 工资周期 | 每周一凌晨 4:00 重置；未领取不补发 |
| 活跃度阈值 | 活跃度 ≥ 200 方可领取工资 |
| 门派经验 | 全成员试炼 + 捐献活跃度总和 = 门派总经验 |
| 退出门派 | 原贡献经验保留；新门派活跃从 0 开始 |

### P03 文本输入规则

| 维度 | 规则 |
|------|------|
| 门派名字 | ≤ 5 字（中英文数字标点均占 1 字长度） |
| 门派公告 | ≤ 30 字（同上计算规则） |
| 空值校验 | 名字/公告为空 → 不可提交 |
| 禁止字符 | emoji、繁体字、火星文、代码/富文本注入 → 拒绝并提示 |
| 屏蔽字库 | 命中屏蔽字 → 拒绝修改 |
| 编辑权限 | 仅掌门/副掌门可修改；并发修改以最后成功的为准 |
| 刷新机制 | 其他成员不实时刷新，下次进入后刷新 |

| `draw.xlsx` | 打造概率配置 | 界面显示概率与表一致 |
| `task_type` | 主线任务类型 | 新增任务类型需对表测试 |

**测试策略**：任何含"以配置表为准"的用例，测试前必须获取最新配置表并建立离线验算 Excel。

### P06 荒神战斗技能释放时序

| 阵位 | 第 1 次出场 | 第 2 次出场 | 第 3 次出场 |
|------|-----------|-----------|-----------|
| 天位 | 0 秒 | 30 秒 | 60 秒 |
| 地位 | 8 秒 | 38 秒 | 68 秒 |
| 人位 | 16 秒 | 46 秒 | 76 秒 |

| 规则 | 说明 |
|------|------|
| 服务端战斗 | 天/地/人位各自独立出场释放技能 |
| 客户端战斗 | 按排名（天>地>人）顺序，上阵 N 个荒神分配前 N 个时间槽 |
| 挂机场景 | 天位第 2 次不出现（服务端战斗特殊规则） |
| 荒神免疫 | 不受伤害/治疗/buff/群体技能影响 |
| 战斗结束 | 荒神特效立即消失，不残留 |
| 反伤目标 | 荒神造成伤害的反伤目标是队伍 troop 点 |
| 未脱战限制 | 队伍未脱战时不允许上下阵荒神 |

### P07 神武打造（抽卡机制）

| 维度 | 规则 |
|------|------|
| 打造池 | 按品质分池（紫/橙/红），不同池消耗不同材料 |
| 打造消耗 | 打造 1 次 = 10 个材料；打造 5 次 = 50 个材料 |
| 每日上限 | 每日打造次数有上限（凌晨 4:00 刷新），配表 `parameter.xlsx` |

| 跑马灯 | 打造出红色神武 → 触发全服跑马灯；橙/紫/蓝不触发 |

### P08 月卡 / 永久卡体系

| 维度 | 规则 |
|------|------|
| 卡种 | 超值月卡 + 特权月卡 + 永久卡，三卡独立互不影响 |
| 月卡时长 | 购买 +30 天；上限 180 天；剩余 ≥ 151 天时不可再购 |
| 到期时间 | 最后一天凌晨 4:00 到期（4 小时也算一天） |
| 到期提醒 | 剩余 3 天时发送邮件提醒 |
| 每日奖励 | 需手动领取；未领取不补发；凌晨 4:00 刷新 |
| 特权生效 | 购买后即时生效（挂机效率、boss 掉落、采集加成等） |
| 特权到期 | 到期后特权立即失效；已超出的资源保留不扣除，但不可通过地图继续获取 |
| 掉单处理 | 月卡天数 ≥ 180 天时新购买订单 → 返回等额代金券 |
| 永久卡 | 购买后永久生效；重复购买 → 第二笔生效，第一笔返代金券 |

### P09 跨服分组规则

| 维度 | 规则 |
|------|------|
| 分区依据 | 按开服时间分组（相近时间的服务器分为同一赛区） |
| 排序规则 | 赛区内按战力降序排列 |
| 新服处理 | 新服务器单独分组，不与老服混合 |
| 战力相同 | 战力相同按 UID 排序 |

### P10 装备强化继承规则

装备替换时强化/精炼等级的继承矩阵：

| 已穿戴装备状态 | 新装备状态 | 强化继承 | 精炼继承 |
|--------------|----------|---------|---------|
| 未强化 + 未精炼 | 任意状态 | 不继承 | 不继承 |
| 已强化 + 未精炼 | 未强化 + 未精炼 | 继承 | 不继承 |
| 已强化 + 未精炼 | 其他任意状态 | 不继承 | 不继承 |
| 未强化 + 已精炼 | 未强化 + 未精炼 | 不继承 | 继承 |
| 未强化 + 已精炼 | 其他任意状态 | 不继承 | 不继承 |
| 已强化 + 已精炼 | 未强化 + 未精炼 | 继承 | 继承 |
| 已强化 + 已精炼 | 其他任意状态 | 不继承 | 不继承 |

**核心规则**：仅当新装备完全未养成（未强化+未精炼）时，已穿戴装备的对应养成等级才会继承。否则均不继承。
