# 测试用例设计方法论

> 文档定位：面向新入职 QA 的基础方法论，帮助理解测试用例从需求到落地的书写链路。  
> 重点范围：规范性、基础书写流程、优先级判断、覆盖要素。  
> 配套文档：`测试用例书写标准.md` 提供更完整的模板、示例和检查清单。

---

## 一、测试用例的基本定义

测试用例是对某个功能规则的可执行验证说明。

一条合格用例需要说清楚：

- 在什么前置条件下测试；
- 执行什么明确操作；
- 系统应该产生什么结果；
- QA 如何判断通过或失败。

可以简单理解为：

```text
前置条件 + 操作步骤 + 预期结果 = 一条可执行、可验证的测试用例
```

测试用例不是「想到什么测什么」，也不是「把页面按钮点一遍」，而是把需求规则转化成可执行的验证项。

---

## 二、基础书写链路

写测试用例建议按以下顺序进行：

```text
读需求 → 抽规则 → 拆模块 → 设场景 → 写步骤 → 写预期 → 标优先级 → 自查覆盖
```

### 2.1 读需求

先理解功能目的、业务规则、配置限制和影响范围。

重点阅读：

- 策划案、需求文档、设计文档；
- 配置表、奖励表、状态表；
- UI 稿、交互说明、规则说明；
- 历史 Bug、历史踩坑记录。

### 2.2 抽规则

把需求中的自然语言转成可验证规则。

例如：

```text
玩家等级达到30级后开启活动
```

应拆成：

- 等级小于 30：不可进入；
- 等级等于 30：可以进入；
- 等级大于 30：可以进入。

### 2.3 拆模块

不要直接开始写用例，先按功能结构拆模块。

常见拆法：

- 入口与解锁；
- 主流程；
- 分支流程；
- 奖励与消耗；
- 状态流转；
- 异常与边界；
- 关联模块回归。

### 2.4 设场景

每条用例只验证一个核心场景。

场景命名建议使用：

```text
条件 + 操作 + 验证点
```

示例：

- `等级不足时点击活动入口`；
- `背包已满时领取奖励`；
- `积分相同时按战力排序`。

### 2.5 写步骤

步骤必须能被新人直接执行。

要求：

- 操作顺序清晰；
- 页面入口明确；
- 输入数据明确；
- 特殊时机明确，例如断网、重登、跨天、结算瞬间。

### 2.6 写预期

预期结果必须能判断通过或失败。

优先写清楚：

- 界面展示；
- 按钮状态；
- 提示文案；
- 奖励、消耗、次数、积分变化；
- 服务端数据；
- 重登后状态。

禁止只写：

- `功能正常`；
- `显示正确`；
- `符合预期`；
- `操作成功`。

### 2.7 标优先级

根据风险标记 `P0`、`P1`、`P2`、`P3`，不能凭感觉随意标。

### 2.8 自查覆盖

写完后检查是否只覆盖了正常流程，是否遗漏边界、异常、状态、数据和回归影响。

## 三、标准用例结构

推荐基础字段如下：

| 字段 | 作用 | 要求 |
|------|------|------|
| 用例ID | 唯一标识 | 不重复，能看出模块归属 |
| 模块 | 所属范围 | 对应功能拆解模块 |
| 场景 | 验证目标 | 简洁说明测什么 |
| 前置条件 | 执行起点 | 写清账号、配置、时间、数据状态 |
| 测试步骤 | 执行动作 | 清晰、具体、按顺序 |
| 预期结果 | 验收标准 | 具体、可观察、可验证 |
| 优先级 | 风险等级 | 只使用 `P0`、`P1`、`P2`、`P3` |
| 回归层级 | 执行范围 | 冒烟、功能、版本 |

### 3.1 基础模板

```markdown
| 用例ID | 模块 | 场景 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 回归层级 |
|--------|------|------|----------|----------|----------|--------|----------|
| TC-XXX-001 | 入口与解锁 | 满足条件时进入功能 | 账号等级达到X级，功能开关开启 | 1. 登录账号；2. 点击功能入口 | 成功进入功能主界面，默认数据展示正确 | P0 | 冒烟 |
```

## 四、优先级判断

优先级代表风险，不代表编写顺序。

### 4.1 P0：核心阻塞与高风险

满足任一条件，通常应标为 `P0`：

- 影响主流程继续；
- 影响充值、扣费、货币、道具、奖励；
- 影响排行榜、赛季、结算、公平性；
- 可能导致重复发奖、重复扣费、数据丢失；
- 可能导致玩家无法登录、无法进入核心玩法；
- 协议绕过后可能造成资损或非法状态。

常见场景：

- 充值不到账；
- 奖励未发或重复发；
- 消耗失败未回滚；
- 排名结算错误；
- 活动结束奖励错误；
- 重登后关键状态丢失。

### 4.2 P1：关键分支与重要体验

满足任一条件，通常应标为 `P1`：

- 影响关键分支流程；
- 影响状态切换；
- 影响主要 UI 展示或按钮状态；
- 影响红点、邮件、背包、任务等联动；
- 影响弱网、重登、切后台后的恢复；
- 是真实玩家较容易遇到的边界情况。

常见场景：

- 等级不足提示错误；
- 背包满时领取处理异常；
- 红点不消失；
- 按钮置灰状态错误；
- 断线重连后界面状态错误。

### 4.3 P2：一般功能与次要体验

满足以下特征，通常可标为 `P2`：

- 不阻塞主流程；
- 不造成资损；
- 不影响核心规则；
- 影响一般功能体验或次要分支；
- 玩家可以通过其他方式继续完成目标。

常见场景：

- 次要页签刷新异常；
- 非核心红点异常；
- 次要状态展示异常；
- 可绕过的一般交互问题。

### 4.4 P3：轻微表现与优化建议

满足以下特征，通常可标为 `P3`：

- 只影响轻微视觉或体验；
- 不影响功能可用性；
- 不影响规则正确性；
- 不影响玩家核心操作；
- 更接近优化建议。

常见场景：

- 非核心文案不统一；
- 标点、格式、轻微错别字；
- 轻微 UI 对齐、间距问题；
- 低频动画、音效、特效表现瑕疵。

### 4.5 优先级兜底原则

- 一条用例命中多个风险时，取最高优先级；
- 奖励、消耗、扣费、结算、排行、防刷、存档问题默认优先考虑 `P0`；
- 状态切换、关键分支、主要展示、重要联动默认优先考虑 `P1`；
- 不影响规则、不影响资损、不影响主流程，但影响一般体验的问题考虑 `P2`；
- 只影响轻微表现或优化建议的问题才考虑 `P3`。

## 五、覆盖要素

测试用例不能只覆盖主流程。基础覆盖至少包含以下要素。

### 5.1 主流程覆盖

验证功能能按设计正常完成。

包括：

- 入口可见；
- 功能可进入；
- 核心操作可完成；
- 结果正确展示；
- 基础奖励或状态生效。

### 5.2 条件与边界覆盖

验证条件变化时系统是否符合规则。

包括：

- 不满足条件；
- 刚好满足条件；
- 超过条件；
- 次数为 0；
- 资源不足；
- 资源刚好足够；
- 背包、邮件、好友、排行榜等容量上限。

### 5.3 状态流转覆盖

验证功能不同阶段的表现。

包括：

- 未开启；
- 进行中；
- 已完成；
- 结算中；
- 已结束；
- 已领取；
- 已过期；
- 重登后状态保持。

### 5.4 奖励与消耗覆盖

游戏项目中，奖励和消耗是高风险点。

包括：

- 奖励内容与配置一致；
- 奖励数量正确；
- 奖励到账位置正确；
- 重复领取被拦截；
- 消耗成功后精确扣除；
- 失败后不扣除或能回滚；
- 背包满、邮件满、货币上限有兜底。

### 5.5 UI 与交互覆盖

验证玩家可见表现是否符合设计。

包括：

- 标题、图标、文案；
- 按钮状态；
- 页签切换；
- 列表滑动；
- 关闭和返回；
- 红点出现与消失；
- 倒计时和状态提示。

### 5.6 异常与恢复覆盖

验证异常情况下系统是否安全。

包括：

- 弱网；
- 断线重连；
- 切后台；
- 客户端重启；
- 重复点击；
- 请求超时；
- 结算瞬间操作；
- 跨天或跨周期切换。

### 5.7 协议与服务端覆盖

关键规则不能只相信客户端。

包括：

- 条件不足时直接调接口；
- 非当前阶段调用接口；
- 重复请求领奖或扣费；
- 修改请求参数；
- 多端同时操作；
- 服务端是否返回明确错误码；
- 服务端数据是否与客户端一致。

### 5.8 回归影响覆盖

验证当前功能是否影响其他系统。

包括：

- 背包；
- 邮件；
- 任务；
- 成就；
- 红点；
- 排行榜；
- 商城；
- 活动；
- 日志；
- 跨服或合服逻辑。

## 六、最小自查清单

提交用例前，至少检查以下问题：

- [ ] 是否先读需求，再写用例？
- [ ] 是否拆了模块，而不是直接按按钮写？
- [ ] 每条用例是否只验证一个核心场景？
- [ ] 前置条件是否可构造？
- [ ] 步骤是否新人能执行？
- [ ] 预期是否具体可验证？
- [ ] 是否标记了 `P0`、`P1`、`P2`、`P3`？
- [ ] 是否覆盖主流程、边界、状态、异常、回归？
- [ ] 是否遗漏奖励、消耗、结算、防刷等高风险点？
- [ ] 是否删除了「正常」「正确」「符合预期」等模糊表达？

---

## 七、核心记忆

测试用例设计只需要先记住四句话：

1. 先理解规则，再写步骤；
2. 先拆模块，再列用例；
3. 先看风险，再定优先级；
4. 预期必须具体，不能只写正常。
