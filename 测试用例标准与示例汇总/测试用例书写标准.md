# 测试用例书写标准

> 适用对象：新入职 QA、测试用例编写者、AI 辅助生成用例后的人工审核者  
> 适用范围：本项目所有功能测试、专项测试、回归测试、AI 生成测试用例审核  
> 核心原则：**需求先行、拆解完整、用例原子、步骤可执行、预期可验证、风险有优先级**

---

## 一、编写前必须做什么

在写任何测试用例前，必须先完成资料理解和功能拆解，禁止直接凭经验堆用例。

### 1.1 输入资料优先级

优先从以下资料中提取规则：

1. `openspec/` 下的策划案、需求文档、设计文档
2. `spec.md`：需求点、验收标准、主流程、分支流程
3. `design.md`：状态机、服务依赖、异常恢复、持久化、客户端/服务端职责
4. `proposal.md`：业务目标、范围边界、影响面、风险点
5. `tasks.md`：实现落点和回归影响面，仅作补充，不能直接当成业务规则
6. 配置表、Excel、UI 稿、交互稿、历史 Bug、历史踩坑记录

### 1.2 区分两类输入文档

#### A. 策划案 / Excel 转 Markdown

这类文档通常包含字段表、奖励表、状态枚举、UI 标注、数值规则。

重点提取：

- 功能入口、参与条件、解锁条件
- 状态枚举、活动周期、倒计时规则
- 奖励内容、消耗内容、数值边界
- UI 展示、按钮状态、红点规则、异常提示
- 配置字段和可验证的数据条件

#### B. OpenSpec / SDD 风格文档

这类文档通常包含 `Why`、`What Changes`、`Goals`、`Design Decisions`、`Risks` 等内容。

重点提取：

- 业务目标和范围边界
- 状态流转、时序、倒计时、重置规则
- 客户端 / 服务端职责边界
- 异常恢复、离线、重连、持久化规则
- 模块联动、协议约束、回归影响面

### 1.3 信息不足时的处理

- 不允许脑补策划没有给出的数值、文案、公式、奖励。
- 缺少明确配置值时，应写成边界测试点、状态校验点或「待确认项」。
- 待确认项必须集中放在文档末尾，方便找策划、开发确认。

## 二、先拆功能，再写用例

正式写用例前，必须先输出「功能模块拆解树」。拆解树用于保证覆盖完整，避免只写主流程。

### 2.1 推荐拆解维度

可以按以下维度拆：

- 玩家流程：入口 → 解锁 → 操作 → 结算 → 领奖 → 退出
- 系统模块：客户端展示 → 服务端校验 → 数据存储 → 协议交互 → 日志监控
- 时间阶段：未开启 → 进行中 → 结算中 → 已结束 → 下一轮重置
- 状态流转：初始态 → 可操作态 → 已完成态 → 异常态 → 恢复态
- 风险类型：奖励、消耗、排行榜、跨服、并发、弱网、重登、宕机

### 2.2 拆解树模板

```markdown
## 一、入口与准入校验
### 1.1 功能入口显示
### 1.2 解锁条件校验
### 1.3 活动开关 / 灰度 / 服务器限制

## 二、核心操作流程
### 2.1 正常主流程
### 2.2 关键分支流程
### 2.3 重复操作与非法操作

## 三、数值、奖励与消耗
### 3.1 奖励发放
### 3.2 消耗扣除
### 3.3 背包满 / 货币不足 / 次数不足

## 四、状态流转与周期规则
### 4.1 阶段切换
### 4.2 跨天 / 跨周 / 跨赛季重置
### 4.3 结束瞬间与结算瞬间

## 五、异常、协议与回归影响
### 5.1 弱网 / 断线 / 重登
### 5.2 协议绕过与服务端拦截
### 5.3 关联模块回归
```

## 三、标准用例字段

本项目推荐使用 Markdown 表格编写测试用例。基础字段如下：

| 字段 | 是否必填 | 说明 |
|------|----------|------|
| 用例ID | 必填 | 全局唯一，建议包含模块缩写和序号 |
| 模块 | 推荐 | 所属功能模块或拆解树节点 |
| 场景 | 必填 | 一句话说明验证点 |
| 前置条件 | 必填 | 无前置条件时留空，不写「无」 |
| 测试步骤 | 必填 | 明确、可执行、按真实顺序书写 |
| 预期结果 | 必填 | 具体、可观察、可验证 |
| 优先级 | 必填 | 仅允许 `P0`、`P1`、`P2`、`P3` |
| 回归层级 | 推荐 | 冒烟 / 功能 / 版本 |
| 备注 | 可选 | 风险说明、待确认项、配置来源 |

### 3.1 用例ID命名建议

```text
TC-{模块缩写}-{子模块缩写}-{三位序号}
```

示例：

- `TC-F03-SK-001`：战斗系统 - 技能释放 - 第 1 条
- `TC-F09-PAY-001`：商城充值 - 支付流程 - 第 1 条
- `TC-F14-SEASON-001`：周期赛事 - 赛季循环 - 第 1 条

## 四、优先级标准

本项目仅允许使用 `P0`、`P1`、`P2`、`P3`。

### 4.1 P0：核心阻塞 / 资损 / 主链路

出现问题会导致玩家无法继续、严重资损、核心玩法不可用或线上重大事故。

常见 P0：

- 登录、创建角色、进入主城、核心战斗、主线推进
- 充值不到账、重复扣费、金额篡改、支付签名异常
- 奖励未发、重复发奖、消耗未扣、失败不回滚
- 排行榜结算错误、赛季奖励错误、晋级名额错误
- 存档丢失、回档、跨天重置错误、活动结算错误
- 协议绕过导致非法领奖、非法购买、非法晋级

### 4.2 P1：关键分支 / 状态 / 联动

影响主要体验或功能完整性，但通常不直接阻断全部玩家。

常见 P1：

- 关键分支流程异常
- 状态切换错误、按钮状态错误、红点联动错误
- 断线重连、切后台、弱网后的状态恢复
- 背包满、次数不足、等级不足、货币不足等边界
- 多端登录、重复点击、快速切页、并发操作
- 主要 UI 展示异常、关键提示文案错误

### 4.3 P2：一般功能 / 次要分支 / 可绕过体验问题

影响一般功能体验或次要分支，但不阻断主流程，不造成资损，通常可通过其他路径继续使用。

常见 P2：

- 次要入口、次要页签、非核心列表刷新异常
- 非核心红点、非核心提示、次要状态展示异常
- 低频边界条件下的体验问题
- 可绕过、不影响最终结果的一般交互问题

### 4.4 P3：轻微表现 / 建议优化 / 极低风险

影响很轻，主要是表现、文案、视觉或优化建议，不影响规则正确性和功能可用性。

常见 P3：

- 非核心文案不统一、标点或格式问题
- 轻微 UI 对齐、间距、遮挡但不影响操作
- 低频动画、音效、特效表现瑕疵
- 规则说明中的轻微展示问题
- 体验优化建议

### 4.5 优先级兜底规则

- 一条用例覆盖多个风险时，取最高优先级。
- 奖励发放、消耗扣除、排行结算、存档回档、重复发奖、扣费异常默认不低于 `P0`。
- 状态切换、关键分支、主要展示异常默认不低于 `P1`。
- 只有不影响主流程、不影响资损、不影响规则正确性的问题，才考虑 `P2` 或 `P3`。

## 五、回归分层标准

| 回归层级 | 覆盖范围 | 使用场景 |
|----------|----------|----------|
| 冒烟回归 | P0 主流程和核心可用性 | 每日构建、提测后快速验收 |
| 功能回归 | P0 + P1 | 功能完整测试、版本内多轮回归 |
| 版本回归 | P0 + P1 + 高风险 P2，按需抽查 P3 | 发版前总回归、专项回归 |

### 5.1 系统首次接入必测

- 功能入口和解锁条件
- 红点联动
- 奖励发放和消耗扣除
- 背包满转邮件或失败兜底
- 重登后数据持久化
- 日志、错误码、协议返回

### 5.2 高风险玩法每次回归

- 奖励发放、重复发奖、防刷
- 消耗扣除、失败回滚
- 跨天重置、活动结束瞬间、赛季结算
- 排行榜排序、同分兜底、奖励分档
- 弱网、断线重连、多端并发

## 六、好用例的五项标准

| 标准 | 要求 | 常见反例 |
|------|------|----------|
| 可读性 | 语言清晰，无歧义 | 「测试活动是否正常」 |
| 可执行性 | 新人按步骤能执行 | 「进入相关界面操作一下」 |
| 独立性 | 尽量不依赖上一条用例结果 | 「接上一条继续领取」 |
| 原子性 | 一条用例只验证一个核心点 | 同时验证入口、领奖、排行、红点 |
| 可验证性 | 预期具体可观察 | 「功能正常」「显示正确」 |

## 七、字段书写规范

### 7.1 场景写法

场景要说明「验证对象 + 条件 + 目标」。

好例子：

- `等级不足时点击活动入口`
- `背包已满时领取通关奖励`
- `积分相同且战力相同时按 UID 排序`

坏例子：

- `测试入口`
- `测试领奖`
- `排行榜正常`

### 7.2 前置条件写法

前置条件必须是可构造、可达到的明确状态。

好例子：

```text
账号A完成新手引导且等级为10级，背包内已有道具「挑战券」x1，活动开关开启。
```

坏例子：

```text
账号等级较高，数据正常。
```

必须写清楚的前置条件包括：

- 账号等级、任务进度、VIP 等级、开服天数
- 活动开关、灰度配置、服务器分组、跨服状态
- 背包容量、货币数量、道具数量、挑战次数
- 网络状态、登录状态、时间点、客户端版本

### 7.3 测试步骤写法

步骤必须是明确操作，不能写抽象命令。

好例子：

```text
1. 登录账号A，进入「阵营竞技」主界面。
2. 点击「报名」按钮。
3. 关闭客户端并重新登录账号A。
4. 再次进入「阵营竞技」主界面，查看报名状态。
```

坏例子：

```text
测试报名功能，检查是否正常。
```

步骤书写要求：

- 每一步只写一个明确动作。
- 涉及输入时必须给具体值。
- 涉及跨页面、重登、断网、切后台、改时间时，必须写明发生时机。
- 不要把多个条件揉在一步里。

### 7.4 预期结果写法

预期结果必须和步骤或验证点一一对应，优先写具体数值、状态、文案、界面变化。

好例子：

```text
1. 点击后弹出提示「报名成功」。
2. 报名按钮置灰，按钮文案变为「已报名」。
3. 重登后仍展示「已报名」状态，服务端报名记录未丢失。
```

坏例子：

```text
报名成功，功能正常。
```

预期结果必须覆盖：

- 客户端展示是否正确
- 服务端数据是否正确
- 奖励 / 消耗 / 次数是否准确
- 失败场景是否有提示、是否回滚
- 重登后数据是否一致

## 八、游戏项目通用测试维度

写完用例后，必须按以下维度自查是否遗漏。

### 8.1 功能解锁

- 满足条件时入口显示且可点击
- 不满足条件时入口隐藏、置灰或提示解锁条件
- 部分满足条件时不能提前进入
- 刚解锁首次进入时数据初始化正确

### 8.2 红点逻辑

- 有可领奖励、可操作次数、未查看内容时红点出现
- 奖励领取、次数耗尽、内容已查看后红点消失
- 子入口红点能正确传递到父入口
- 跨天、重登后红点状态刷新正确

### 8.3 奖励与消耗

- 奖励内容、数量、品质与配置一致
- 领取后背包、邮件、货币余额正确变化
- 重复领取被拦截
- 背包满、邮件满、货币上限时有明确兜底
- 消耗失败时不扣资源，成功时精确扣除

### 8.4 状态与周期

- 未开启、进行中、结算中、已结束状态正确
- 跨天、跨周、跨赛季重置正确
- 活动结束瞬间、结算瞬间、领奖瞬间不出现竞态
- 重登后状态与服务端一致

### 8.5 排序与排行榜

- 排序优先级符合规则
- 同分、同战力、同时间等兜底规则明确
- 排名变化后奖励分档正确
- 结算中数据冻结，不允许继续刷分影响结果

### 8.6 UI展示与交互

- 标题、图标、文本、规则说明正确
- 按钮状态、置灰、倒计时、页签切换正常
- 列表滑动、分页、刷新、空状态正确
- 关闭、返回、切后台、断线恢复后界面正常

### 8.7 异常与协议

- 非当前阶段调用接口被拒绝
- 条件不足时绕过客户端直接请求被服务端拦截
- 重复点击、快速点击、多端同时操作不会重复生效
- 弱网、断线、超时、服务重启后数据不丢、不重发

## 九、边界与异常必须拆成独立用例

禁止在一条用例的预期中写「如果是 A 则 B，如果是 C 则 D」。只要条件不同，就必须拆成独立编号的用例。

### 9.1 边界值写法

例如等级门槛为 30 级，应至少拆成：

| 用例ID | 场景 | 前置条件 | 测试步骤 | 预期结果 | 优先级 |
|--------|------|----------|----------|----------|--------|
| TC-DEMO-LEVEL-001 | 29级玩家进入功能 | 账号等级为29级 | 点击功能入口 | 入口不可进入，提示达到30级后开启 | P1 |
| TC-DEMO-LEVEL-002 | 30级玩家进入功能 | 账号等级为30级 | 点击功能入口 | 成功进入功能主界面 | P0 |
| TC-DEMO-LEVEL-003 | 31级玩家进入功能 | 账号等级为31级 | 点击功能入口 | 成功进入功能主界面 | P1 |

### 9.2 条件矩阵写法

如果准入条件是「等级 ≥ 30 且开服天数 ≥ 7」，不能只写一条「不满足不能进」。应拆成矩阵：

| 等级 | 开服天数 | 预期 |
|------|----------|------|
| 29 | 6 | 不能进入，提示条件不足 |
| 29 | 7 | 不能进入，提示等级不足 |
| 30 | 6 | 不能进入，提示开服天数不足 |
| 30 | 7 | 可以进入 |
| 31 | 8 | 可以进入 |

## 十一、示例：合格用例与不合格用例

### 11.1 合格用例

| 用例ID | 模块 | 场景 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 回归层级 |
|--------|------|------|----------|----------|----------|--------|----------|
| TC-F14-REWARD-001 | 奖励结算 | 淘汰赛8进4失败后发放淘汰奖励 | 账号A已进入淘汰赛8进4，对应奖励配置为「元宝x100、荣誉x50」 | 1. 使用账号A完成8进4战斗并失败；2. 返回赛事主界面；3. 打开邮件或奖励入口；4. 记录元宝和荣誉变化；5. 重新登录账号A再次检查奖励状态 | 1. 账号A被标记为8进4淘汰；2. 奖励按配置发放「元宝x100、荣誉x50」；3. 再次登录后奖励状态保持已发放；4. 重复领取被拦截，不重复发奖 | P0 | 功能 |

为什么合格：

- 前置条件明确，可构造。
- 步骤按真实执行顺序书写。
- 预期包含状态、奖励数值、重登持久化、防重复领取。
- 聚焦一个核心风险：淘汰奖励是否正确发放。

### 11.2 不合格用例

| 用例ID | 场景 | 步骤 | 预期结果 | 优先级 |
|--------|------|------|----------|--------|
| TC-BAD-001 | 测试赛事奖励 | 打一场比赛看看奖励 | 奖励正常 | P0 |

问题：

- 没有前置条件，不知道账号处于哪个阶段。
- 步骤不可执行，不知道打哪一场、胜负如何构造。
- 预期不可验证，没有奖励名称、数量、发放方式。
- 没有验证重登、防重复、状态变化。

## 十二、AI 生成用例后的人工审核清单

AI 可以辅助生成测试用例，但最终必须由 QA 人工审核。

### 12.1 必查项

- 是否先做了功能模块拆解，而不是直接列用例。
- 是否引用了项目资料、策划规则、配置表，而不是凭空编写。
- 是否覆盖主流程、分支、边界、异常、协议、回归影响。
- 是否所有奖励、消耗、积分、次数、概率、公式都有明确数值或待确认标记。
- 是否每条用例只验证一个核心点。
- 是否存在「功能正常」「显示正确」「符合预期」等空泛预期。
- 是否把不同条件拆成独立用例，而不是混在一条里。
- 是否遗漏重登、弱网、断线、多端、跨天、结算瞬间等高风险场景。

### 12.2 必删或必改的反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 只有正常流程 | 漏掉边界和异常 | 增加不足、超限、重复、非法、失败回滚 |
| 一条用例多个判断 | 执行和定位问题困难 | 按条件拆成独立用例 |
| 预期写「正常」 | 无法验收 | 写具体文案、数值、状态、数据变化 |
| 脑补数值 | 可能和策划不一致 | 标注待确认或引用配置来源 |
| 只看客户端 | 漏掉服务端防刷 | 增加协议绕过、重复请求、服务端数据校验 |
| 忽略持久化 | 重登后容易丢状态 | 增加重登、切服、服务重启校验 |

## 十三、最终提交前自检

提交测试用例前，逐项检查：

- [ ] 是否已阅读需求 / 策划 / 配置 / UI / 历史 Bug？
- [ ] 是否已完成「功能模块拆解树」？
- [ ] 每个需求点是否至少有 1 条用例覆盖？
- [ ] P0 是否覆盖主流程、资损、结算、存档、防刷？
- [ ] P1 是否覆盖关键分支、状态、边界、联动？
- [ ] P2/P3 是否用于一般体验、轻微表现或低风险问题，未误标高风险场景？
- [ ] 是否有足够的异常场景和协议绕过场景？
- [ ] 前置条件是否可构造？
- [ ] 步骤是否新人可执行？
- [ ] 预期是否具体到数值、状态、文案或数据变化？
- [ ] 是否删除了「正常」「正确」「符合预期」等空泛表达？
- [ ] 是否把待确认项集中列出？
- [ ] 是否标明优先级和回归层级？

## 十五、一句话记忆

好测试用例不是「我知道怎么测」，而是「任何新人拿到后，都能按步骤复现，并明确判断通过或失败」。
