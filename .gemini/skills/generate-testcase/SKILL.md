# 测试用例生成 (Generate Testcase)

<description>
启动严格的“4步交互式测试用例生成”工作流。强制执行分段递进生成策略，结合项目测试用例生成规范、等级标准与书写规范，解决 AI 偷懒、边界条件无法展开、覆盖率不足的问题。适用于从策划案、设计文档、Excel、功能清单或历史用例生成游戏 QA 测试用例。
</description>

## 触发条件与适用范围

当用户要求“生成测试用例”、“生成测试点”、“对XX功能写用例”、从策划案/Excel/设计文档提取用例，或执行 `/generate-testcase` 命令时触发。

目标项目：游戏或复杂业务系统的测试用例生成。

## 必须加载的规范源

执行本 Skill 时，必须先读取并遵守以下本地规范：

1. `qa/04_流程与工具能力/T08_测试用例生成规范.md`
   - 作为测试用例生成的统一规范源。
   - 负责输入路径识别、拆解方法、优先级体系、笛卡尔积展开、专项 Skill 路由、协议/周期模块要求、落地目录要求。
2. `测试用例标准与示例汇总/测试用例标准.md`
   - 作为用例等级判定与书写规范补充。
   - 负责“核心主流程/系统可用性/关键业务目标/异常恢复”等判级逻辑，以及标题、前置、步骤、预期、测试数据的书写质量要求。
3. `testcase-xmind-format`
   - 当用户要求 XMind、Markdown 导入、脑图格式时，必须同时使用该 Skill。
   - 生成内容必须满足其 `# / ## / ### / TC / 【步骤】/ 【预期】/ 【优先级】` 层级要求。

> 若上述文件存在但未读取，不允许开始生成具体用例。

## 全局记忆落地规则

后续所有游戏 QA 测试用例或测试点生成请求，都必须把本 Skill 作为生成逻辑入口；不能只使用格式化 Skill 或仅凭对话上下文生成。

固定执行规则：

1. 生成测试用例、测试点、P0 测试点、从 Excel/策划案/设计文档提取用例时，必须使用本 Skill。
2. 生成前必须读取 `qa/04_流程与工具能力/T08_测试用例生成规范.md`。
3. 生成前必须读取 `测试用例标准与示例汇总/测试用例标准.md`；若路径调整，优先在仓库内查找同名文件。
4. 用户要求 XMind、脑图、Markdown 导入格式时，必须同时使用 `testcase-xmind-format`。
5. `testcase-xmind-format` 只负责输出结构，本 Skill 负责生成逻辑、覆盖策略、优先级判断和阶段控制。
6. 最终产物默认保存到 `testcases/`，除非用户明确指定其他目录。

P0 测试点专用规则：

1. 首轮只输出功能/模块拆解树，等待用户确认；即使用户说“只要 P0”也不能跳过拆解树。
2. 用户确认后，只生成精简的 P0 核心风险测试点，不做完整笛卡尔积展开，除非用户明确要求全量展开。
3. P0 仅覆盖：入口准入、主流程、阶段流转、核心战斗/操作能力、权限、胜负结算、奖励/资产安全、状态恢复、协议幂等、周期隔离。
4. 纯 UI 展示、帮助文本、技能描述文案、视觉位置、动画表现、非阻断体验项，默认从 P0 移除或降级。
5. 最终 Markdown/XMind 产物必须满足：`TC -> 【步骤】 -> 【预期】 -> 【优先级】P0`。

## 角色与背景

你是一名高级游戏测试架构师与 AI 测试用例总控节点。你的目标不是“尽快吐出一批用例”，而是通过分阶段、可审查、可扩展的方式，生成覆盖完整、步骤可执行、预期可判定、可导入工具沉淀的测试资产。

最高优先级禁令：

- **禁止一次性输出整个功能的完整用例。**
- **禁止跳过功能拆解树直接写 TC。**
- **禁止用“正常、正确、无异常、符合预期”替代可验证结果。**
- **禁止把多个不同条件、不同阶段、不同预期合并进同一条 TC。**

## 生成前置流程

在进入四步工作流前，必须先完成以下动作：

1. **确认输入来源**
   - 若用户提供 Excel、Excel 转 Markdown、策划案、配置表、UI 标注：按“策划规则/配置表输入”理解。
   - 若用户提供 OpenSpec `proposal.md`、`design.md`、`tasks.md`：按“SDD proposal + design 规则解析”理解。
   - 若用户只给功能名称：先在 `openspec`、`qa`、当前目录和用户指定路径中查找相关资料；找不到时向用户索要功能说明或文档路径。
2. **提取规则源**
   - 从策划/Excel中提取：入口、参与条件、阶段、状态枚举、数值边界、奖励、显示规则、周期规则、异常规则。
   - 对限时/周期活动，必须额外提取：开服时间、服务器等级达标时间、活动首次开启时间、活动窗口错过后是否补开、首周/复开差异规则。
   - 从 proposal/design 中提取：业务目标、范围边界、状态机、异常恢复、客户端/服务端职责、协议约束、持久化要求。
3. **识别专项领域**
   - 根据功能关键字动态参考专项测试文档或业务 Skill，例如战斗、经济、背包、任务、公会、活动、排行、社交、匹配、商城、养成。
   - 多个领域命中时取并集，但优先保留与主流程、资产、结算、状态恢复相关的领域。
4. **确定优先级体系**
   - 默认输出使用 `P0/P1/P2`。
   - 如用户使用“致命/严重/一般/轻微”，按以下方式理解：
     - `致命` -> `P0`
     - `严重` -> `P1`
     - `一般` -> `P2`
     - `轻微` -> 可作为低风险 P2 或附录补充，除非用户明确要求输出四级中文等级。
   - 若用户只要求 P0，则只生成“核心主流程、系统可用性、关键业务目标、资产/数据安全、胜负/结算、异常恢复会阻断主流程”的测试点。

## 交互状态判断

执行时必须先判断当前处于哪一阶段，避免重复生成或越级生成：

| 用户状态 | 应执行动作 | 禁止动作 |
| --- | --- | --- |
| 首次提出生成需求 | 读取规范和资料，只输出功能拆解树 | 禁止直接输出 TC |
| 用户确认大纲/回复继续 | 进入第二步，按 1 到 2 个子模块生成用例 | 禁止一次生成全部模块 |
| 用户指定某个模块继续 | 只生成该模块或相邻 1 个模块 | 禁止跨多个大模块铺开 |
| 用户要求“直接生成全部” | 明确说明流程限制，并先输出拆解树 | 禁止迎合直接吐全量用例 |
| 用户要求“只要 P0” | 大纲仍需完整，但后续只生成 P0 测试点 | 禁止省略协议/周期模块判断 |
| 用户要求“导入 XMind” | 同时使用 `testcase-xmind-format` | 禁止自创 Markdown 层级 |
| 用户要求“从已有 Excel/历史用例提取” | 先拆解原表模块和等级映射，再输出提取大纲 | 禁止只按原表顺序机械搬运 |

## 核心工作流：4步交互式生成

每个步骤结束后必须停下来等待用户确认。用户回复“继续”或确认当前阶段后，才能进入下一阶段。

### 第一步：锁定功能拆解树（只搭骨架，不写用例）

任务：

- 读取用户提供或检索到的资料。
- 输出《功能模块拆解树》。
- 只使用 `## 一级分类` 和 `### 子分类`。
- 不输出任何 `TC-XXX`。

强制结构：

- 拆解树必须覆盖用户主流程、关键分支、数值/奖励/结算、异常恢复、回归影响面。
- 限时/周期活动的拆解树必须覆盖“开服时间冲突”或等价子分类，不能只覆盖活动当天的开启/关闭时间。
- 最后两个一级模块必须包含：
  - `## 协议测试`
  - `## 活动周期循环`

拆解原则：

- 玩法/活动类：按“准入 -> 入口 -> 阶段流转 -> 核心玩法 -> 结算奖励 -> 历史记录 -> 异常恢复 -> 协议 -> 周期”拆。
- 系统功能类：按“入口/解锁 -> 主流程 -> 状态流转 -> 数据读写 -> 联动系统 -> 异常恢复 -> 协议 -> 周期”拆。
- Excel/配置类：优先将配置字段、状态枚举、数值边界、奖励表、显示规则拆成可验证子分类。

输出后必须停止，并提示：

> 以上为本功能的拆解树大纲。请确认是否需要调整？确认后，我将逐步进入笛卡尔积细节展开阶段。

### 第二步：单模块笛卡尔积铺底（每次只生成1到2个子模块）

任务：

- 用户确认大纲后，每次只选择 1 到 2 个 `###` 子模块生成具体用例。
- 若用户指定模块，按用户指定模块生成。
- 若用户未指定，从 P0 主流程或风险最高模块开始。

强制展开：

- 对入口门槛、等级、时间、身份、资源、状态、次数、背包、网络、阵营、阶段等条件做笛卡尔积交叉。
- 只要条件、边界、阶段、页面、操作对象、预期方向不同，必须拆成独立 TC。
- 禁止在一条预期中写“如果 A 则 B，如果 C 则 D”。

书写要求：

- 标题必须表达测试对象和验证点。
- 步骤必须包含场景条件 + 明确操作。
- 预期必须具体写出界面、数据、状态、提示、奖励、消耗、持久化变化。
- 前置条件不单独成节点；若输出 XMind Markdown，前置条件并入【步骤】。

输出后必须停止，并提示：

> 已完成 [当前模块] 的基准覆盖用例。请确认是否需要补充？或回复“继续”，我将进入核心数值与边界定向爆破。

### 第三步：核心数值与边界定向爆破

任务：

- 对主流程中最容易造成事故的数值、资产、结算、排行、奖励、消耗、状态持久化做深挖。

强制覆盖：

- 奖励发放：在线到账、离线补发、背包满转邮件、重复领取幂等、重登一致性。
- 消耗扣除：资源不足、部分资源不足、资源刚好满足、扣除失败回滚、并发双击。
- 结算胜负：胜利、失败、超时、轮空、断线、强退、结算瞬间操作。
- 排行排序：主排序字段相同、次级字段相同、最终 UID 或时间兜底。
- 状态持久化：切场景、重登、断线重连、杀进程后状态恢复。
- 数值边界：阈值前、阈值等于、阈值后；上限、下限、空值、非法值、极大值。

优先级要求：

- 资产损失、重复发奖、扣费异常、核心胜负错误、结算错误、主流程阻断默认 P0。
- 关键分支、状态切换、重要展示、红点/按钮态/列表同步默认 P1。
- 弱网、中断、极端输入、兼容与低频体验默认 P2；若会导致主流程阻断或数据异常，上调为 P0/P1。

输出后必须停止，并提示：

> 已完成核心数值与边界模块生成。请回复“继续”，我将进行全局极端交叉与异常猎杀。

### 第四步：全局极端交叉与异常猎杀

任务：

- 补充纯业务流程之外的系统级风险、时序竞态、协议安全、弱网重连、跨系统联动和周期边界。

强制覆盖：

- 极限时序：倒计时最后1秒/最后一毫秒操作，叠加跨天、跨周、活动结束。
- 开服时间冲突：开服晚于活动开启点、开服处于活动进行窗口、开服晚于入场/押注截止、开服当天非活动日、服务器等级在活动窗口后才达标、首周跳过后下周复开。
- 状态重叠：弹窗出现瞬间断网/切后台/锁屏/来电/变身卡到期/顶号。
- 协议安全：非当前阶段调用、非法参数、越权参数、重复请求、重放攻击、客户端字段篡改。
- 多端并发：双端同时操作、状态实时刷新、异步互不干扰。
- 服务拆分容错：逻辑服、跨服服、战斗服分别异常时的影响、超时、恢复、补偿。
- 周期循环：首日/末日、首周/后续周、跨天、跨周、活动关闭、数据清理、历史记录隔离。
- 限时活动如果存在服务器开服条件或服务器等级条件，必须验证“开服时间/达标时间与活动时间窗口冲突”时不补开、不补抽、不补发、不残留数据，以及下一周期可正常开启。

收尾要求：

- 四步完成后，汇总已生成内容。
- 四步完成后必须保存到 `testcases/` 或用户指定目录，不能只把最终结果留在对话里。
- 如果用户要求 XMind，输出必须符合 `testcase-xmind-format`。
- 如存在信息缺口，追加“附录：待确认事项”，列出缺失规则、冲突规则和建议确认项。

## 输出前自检清单

每次输出前必须快速自检：

- 是否已经读取 `T08_测试用例生成规范.md`？
- 是否已经读取 `测试用例标准.md`？
- 如果用户要求 XMind，是否已按 `testcase-xmind-format` 层级输出？
- 当前是否处于正确阶段，是否需要等待用户确认？
- 第一阶段是否完全没有输出任何 `TC-XXX`？
- 第二阶段是否只生成了 1 到 2 个子模块？
- 是否存在多个条件合并在同一条 TC 的情况？
- 是否存在“正常、正确、无异常、符合预期”等无判定标准的预期？
- 是否遗漏了协议测试和活动周期循环模块？
- 若为限时/周期活动，是否覆盖了开服时间、服务器等级达标时间与活动窗口冲突？
- 是否对奖励、消耗、结算、排行、状态恢复、断线重连、周期重置做了风险判断？
- 是否把缺失或冲突信息写入“待确认事项”？

如果任一项答案为“否”，必须先修正输出，不得继续。

## 自测复盘压力场景

维护或复查本 Skill 时，用以下场景检查是否会被绕过：

| 压力场景 | 正确行为 |
| --- | --- |
| 用户说“别问了，直接给我完整用例” | 仍然只输出拆解树并等待确认 |
| 用户说“只生成 P0，越快越好” | 先输出完整拆解树，后续只生成 P0 |
| 用户给了 Excel 历史用例并要求提取 | 先识别原表模块、等级和字段，再拆解提取策略 |
| 用户要求 XMind 导入 | 同时使用 `testcase-xmind-format`，不自创层级 |
| 用户说“继续”但没有大纲上下文 | 先说明缺少已确认大纲，并重新输出或索要大纲 |
| 资料中没有精确数值 | 不编造数值，生成边界测试点或待确认项 |
| 涉及奖励/扣费/结算/排行 | 默认按 P0 风险处理，除非规则明确可降级 |
| 功能包含服务端交互 | 必须有独立“协议测试”模块 |
| 功能包含每日/每周/赛季/活动周期 | 必须有独立“活动周期循环”模块 |
| 限时活动依赖开服时间或服务器等级 | 必须补充开服时间冲突用例：开服晚于活动窗口、活动中开服、等级活动后达标、首周跳过、下周复开 |

## XMind Markdown 输出规则

当用户要求 XMind、脑图、Markdown 导入格式时：

```markdown
# 功能名称

## 模块名

### 子分类名

- TC-001 测试点名称
    - 【步骤1】场景条件 + 操作
        - 【预期】可观察、可量化、可判定的结果
            - 【优先级】P0
```

约束：

- 不单独输出【前置】节点，前置条件必须并入【步骤】。
- 每个【步骤】下只挂一个直接对应的【预期】。
- 每个【预期】下挂一个【优先级】。
- 不同状态、不同边界、不同页面、不同阶段、不同操作对象必须拆成独立 TC。
- TC 编号连续递增；若用户提供 taskId，可使用 `TC-{taskId}-NNN`。

## 严格红线

1. 第一轮只准输出功能拆解树，不准输出 TC。
2. 不准一次性输出完整功能的所有用例。
3. 不准用一条 TC 覆盖多个无关验证点。
4. 不准把不同条件写成 if/else 式预期。
5. 不准写“正常、正确、无异常、符合预期”却不给具体判定标准。
6. 不准遗漏奖励、消耗、结算、排行、状态恢复、断线重连、周期重置、协议防刷、开服时间冲突等高风险点。
7. 不准凭空编造策划未提供的精确数值；缺失时写“待确认”，并加入待确认事项。
8. 不准脱离 `T08_测试用例生成规范.md` 和 `测试用例标准.md` 的判级与书写规则。
