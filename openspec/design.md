## Context

游戏5分钟时（击败虎先锋后），需要增加一个1小时的目标感。拯救魔蝎是一个多阶段限时任务系统，提供明确的阶段目标和倒计时压力。当前代码库已有成熟的模块系统、UI组件系统、倒计时系统和红点系统，需要复用这些基础设施。

现有相关系统：
- **任务面板**: 位于主界面，需要在其上方新增入口
- **日常任务模块** (`DailyQuest`): 任务进度跟踪、奖励领取、红点集成的最佳参考
- **倒计时系统**: 使用 `SLApp.Api.RegisterTimer()` 实现，支持毫秒级更新
- **红点系统**: 基于 `RedDotService` 的树形结构，支持层级聚合
- **功能解锁系统**: 基于 `function_level` 表的条件检查
- **Spine动画**: 使用 `UISpine` 组件加载立绘

## Goals / Non-Goals

**Goals:**
- 实现拯救魔蝎入口，在击败虎先锋后显示在任务面板上方
- 实现多阶段任务系统，完成上一阶段解锁下一阶段
- 实现每阶段独立倒计时，毫秒级实时变动
- 实现离线超时处理：上线时继续计数（若离线期间结束则重新开始）
- 实现奖励领取和红点系统集成
- 复用现有模块系统、UI组件系统、倒计时和红点系统

**Non-Goals:**
- 不实现剧情对话系统（后续版本）
- 不实现阶段间过渡动画（使用刷新+锁减少）
- 不实现多语言支持
- 不修改现有红点系统的核心逻辑

## Decisions

### 1. 模块架构
**决策**: 创建 `RescueScorpionModule` 继承 `FunctionModule`，依赖 `TaskModule`、`FuncCheckModule`

**理由**: 
- 遵循现有模块模式（如 `GodEquipDungeonModule`）
- 复用 `function_level` 表的解锁检查逻辑
- 模块生命周期自动管理

**替代方案**: 
- 在 `TaskModule` 中添加功能（不推荐：违反单一职责，增加耦合）

### 2. 倒计时实现
**决策**: 使用 `SLApp.Api.RegisterTimer(0.1f, ...)` 实现毫秒级更新，客户端本地计算毫秒

**理由**:
- 100ms间隔满足毫秒实时变动需求
- 客户端本地计算避免频繁服务端同步
- 每秒与服务端校准防止漂移

**倒计时归零行为** (TC-023):
- 倒计时结束后立即重新开始当前阶段倒计时
- 不进入下一阶段，仅重置计时器
- 由服务端记录 `stage_start_time`，客户端计算剩余时间

**替代方案**:
- 服务端每秒同步（不推荐：网络开销大，延迟导致显示不流畅）
- 纯客户端计时（不推荐：离线超时处理困难）

### 3. 离线超时处理
**决策**: 服务端记录 `stage_start_time`，客户端计算剩余时间

**理由**:
- 服务端时间作为权威来源
- 上线时重新计算剩余时间
- 支持跨设备同步

**离线计时行为** (TC-024):
- 离线期间倒计时继续计算（不暂停）
- 上线时继续计数（根据服务端 `stage_start_time` 计算剩余时间，继续倒计时）
- 若离线期间倒计时结束，上线时重新开始当前阶段倒计时

**替代方案**:
- 客户端记录（不推荐：跨设备不同步，作弊风险）
- 离线暂停计时（不推荐：与策划案不符，策划案明确"倒计时结束后立即重新开始"）

### 4. 红点系统集成
**决策**: 新增 `RescueScorpionRedDotCheck`，任务红点聚合到入口

**理由**:
- 复用现有红点树形结构
- 支持多任务红点聚合
- 符合现有红点模式

**替代方案**:
- 自定义红点逻辑（不推荐：重复造轮子，无法与现有系统集成）

### 5. UI架构
**决策**: 创建 `RescueScorpionEntryView`（入口）和 `RescueScorpionMainView`（主界面）

**理由**:
- 入口是轻量级组件，适合独立组件
- 主界面是复杂弹窗，适合 `UIFunction`
- 复用现有UI组件模式

**替代方案**: 
- 单一组件（不推荐：职责不清，代码臃肿）

### 6. 任务系统参考
**决策**: 任务进度跟踪、状态管理和奖励领取逻辑参考日常任务模块（`DailyQuest`）

**理由**:
- 日常任务模块已实现成熟的数据模型（`TaskItemData`、`CommonTaskConfig`）
- 复用进度计算逻辑（`TaskData.GetTaskProgressValue`）
- 复用奖励领取模式（`SendGetAward`）
- 复用红点集成模式（`DailyQuestRedDotCheck`）

**参考文件**:
- `DailyQuest/DailyQuestAbility.cs` - 任务业务逻辑
- `DailyQuest/Data/DailyQuestData.cs` - 数据管理和网络通信
- `DailyQuest/UI/DailyQuestUI.cs` - UI控制器
- `Quest/QuestViewUI.cs` - `TaskItemData` 和 `CommonTaskConfig` 类定义

### 7. 阶段解锁条件
**决策**: 完成当前阶段所有任务（领取全部奖励）后解锁下一阶段 (TC-010)

**理由**:
- 策划案明确"完成上一阶段任务后可以进入下一阶段"
- 任务状态有三种：未完成、可领取、已领取
- 只有所有任务变为"已领取"状态才算完成阶段

**解锁判断逻辑**:
```csharp
bool CanUnlockNextStage()
{
    return currentStageTasks.All(task => task.IsGot);
}
```

### 8. 阶段奖励发放
**决策**: 
- 阶段任务奖励：手动领取（点击"领取"按钮）
- 全部阶段完成大奖：自动发放 (TC-028)

**理由**:
- 阶段任务奖励需要玩家主动领取，提供参与感
- 全部阶段完成后自动发放大奖，提供成就感
- 神将奖励自动播放秀将界面

### 9. 断网领取处理
**决策**: 断网时允许点击领取按钮，请求失败后显示网络错误提示，重连后需重新点击 (TC-047)

**理由**:
- 系统无离线请求队列（参考 `ServerService.SendRequest` 实现）
- 断网时请求只会记录警告，不会被发送
- 重连后游戏模块收到 `ReFlushUserAfterSignal` 刷新数据，但请求不会自动重发
- 玩家需在重连后重新点击领取按钮

**实现参考**:
- `ServerService.cs` - `SendRequest` 方法：未登录时只记录警告
- `ServerService.Reconnect.cs` - 重连逻辑：最多3次自动重连，每次5秒超时
- 重连后通过 `ReFlushUserAfterSignal` 通知游戏模块刷新数据

**替代方案**:
- 本地缓存领取请求（不推荐：系统未实现此机制）
- 离线领取（不推荐：无法保证数据一致性）

## Risks / Trade-offs

**Risk**: 倒计时精度问题 → 客户端本地计时可能漂移
**Mitigation**: 每秒与服务端校准，误差控制在1秒内

**Risk**: 离线超时处理复杂 → 上线时重新计时可能造成玩家困惑
**Mitigation**: UI明确显示"重新开始计时"，提供明确反馈

**Risk**: 红点性能问题 → 多任务红点频繁更新
**Mitigation**: 使用现有红点系统的批量更新机制，避免频繁刷新

**Risk**: 阶段切换状态不一致 → 完成阶段后界面刷新可能延迟
**Mitigation**: 服务端确认后立即刷新UI，使用事件驱动模式
